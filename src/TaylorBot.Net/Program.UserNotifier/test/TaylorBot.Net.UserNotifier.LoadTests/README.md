# User-notifier load testing

Run [`Test-UserNotifierLoad.ps1`](../../Test-UserNotifierLoad.ps1) with Docker running Linux containers. It builds with the pinned .NET SDK and production runtime image, then runs the real notifier in a memory- and CPU-limited worker. PostgreSQL, Redis, schema deployment, synthetic traffic generation, and optional profiling tools run outside that limit. The worker has no external network route and uses synthetic credentials and data only.

```pwsh
.\src\TaylorBot.Net\Program.UserNotifier\Test-UserNotifierLoad.ps1
.\src\TaylorBot.Net\Program.UserNotifier\Test-UserNotifierLoad.ps1 -Profile .\src\TaylorBot.Net\Program.UserNotifier\test\profiles\guild-scale.json
```

The [profiles](../profiles/guild-scale.json) set workload inputs; omitted fields use [`LoadProfile`](./LoadProfile.cs) defaults. Copy a profile to vary cached members, channels, roles, member overlap, message size, event rate, downstream REST latency, or reconnect behavior. `member_count` deliberately differs from cached membership. Guild and shard sizing is based on aggregate production logs; cached membership, channel layouts, and traffic rates are synthetic assumptions, not measured TaylorBot traffic. The [startup](../profiles/startup-pressure.json) and [re-identification](../profiles/reidentify-pressure.json) pressure profiles accelerate entity tracking and increase cached membership to explore failure boundaries, not to prove a production root cause.

The external [controller](../TaylorBot.Net.UserNotifier.LoadController/Gateway.cs) sends real Gateway JSON over WebSockets: startup hydration, sustained traffic, a burst, member churn, message edits/deletions/bulk deletions, role/channel updates, session resumption, fresh identification, and cooldown. Generation is paced with network backpressure, not an unbounded producer queue. Member chunks are generated when Discord.Net requests them. Every tenth guild has moderation logging enabled. Notifier jobs retain application scheduling; external feed/subscriber datasets are empty and Patreon synchronization is disabled.

Startup entity tracking uses the configured per-guild delay. Large profiles can take substantial time to drain, particularly after fresh identification; allow a generous `DeadlineSeconds` when measuring completion. The run deadline is independent of the application's Gateway watchdog. A timeout does not establish a deadlock: inspect background-work progress, READY counts, and application errors. Successful runs require a clean worker exit, no application errors or unexpected REST routes, and exact agreement between sent messages, messages received by Discord.Net, and PostgreSQL channel counts after the real shutdown flush.

Artifacts go into a unique ignored `.load-results` directory, or an empty `-OutputDirectory`. `profile.json` records effective inputs; `samples.jsonl` records phase, actual dispatch counts, managed memory, GC activity, process memory, cgroup memory/events, Discord.Net caches, pending application work, and thread-pool activity. Sampling duration and allocation counts expose measurement overhead inside the worker. `phases.jsonl` records achieved operation timing; `status.json`, `outcome.json`, and `limits.json` record the terminal workload status, container result, and resource limits. Interrupted profiling records `profiler-outcome.json` and `aborted-worker-state.json` before cleanup. `OOMKilled` distinguishes a kernel/container kill from a managed allocation failure in `worker.log`; neither alone identifies the retaining object graph. Process RSS includes shared pages and is not interchangeable with cgroup memory.

Use `-CaptureHeapAtPhase after-identify` or `-CaptureHeapAtPhase cooldown` for an optional synthetic managed heap capture and type-size report. The controller holds the selected phase while collection runs. The profiler has separate resource limits defined in the runner and shares the worker's PID namespace and diagnostic socket volume. Collection still causes work and a full GC inside the worker, can change memory behavior, and may fail near exhaustion; compare an unprofiled run first. `-AllocationTrace` enables runtime GC/allocation events in `allocations.nettrace`, which can be opened in a .NET trace viewer. Trace overhead is also part of the measured worker; keep captures bounded.

`-Cpu` and `-MemoryMiB` support controlled comparisons. `-SkipBuild` reuses the local load images; rebuild after code changes. No production services are read or modified by the harness. It removes only its uniquely named containers, networks, and diagnostic volume; artifacts and local images remain.
